# BPF 子系统核心数据结构

本文依据仓库中的 Linux 6.18.52 源码，以通过 `bpf()` 加载的 eBPF 程序为主线。读数据结构时，先问三个问题：**用户态提交什么，加载后内核保留什么，验证过程中临时计算什么？**`union bpf_attr` 描述请求；`bpf_prog`、`bpf_map`、`bpf_link` 是加载或挂载后可被引用的对象；`bpf_verifier_env` 等结构组织一次加载验证的工作区。指令格式 `bpf_insn` 同时用于用户态提交的指令和内核中的指令区。[版本号](../../linux/Makefile#L1-L5) · [系统调用入口](../../linux/kernel/bpf/syscall.c#L6307-L6310) · [内核指令区](../../linux/include/linux/bpf.h#L1730-L1737) · [验证器工作区分配](../../linux/kernel/bpf/verifier.c#L24943-L24975)

## 1. 先画对象关系

以下是常见的“程序使用 map，并通过 link 挂载”的关系；并非所有 BPF 类型都需要 map，也不是所有挂载方式都产生 `bpf_link`。例如 `BPF_PROG_ATTACH` 与 `BPF_LINK_CREATE` 就是不同命令。[程序引用 map](../../linux/kernel/bpf/verifier.c#L20885-L20915) · [传统 attach 分发](../../linux/kernel/bpf/syscall.c#L6207-L6215) · [link 创建分发](../../linux/kernel/bpf/syscall.c#L5699-L5796)

```text
用户态 bpf(cmd, attr, size)
       │
       ├─ BPF_MAP_CREATE  ──► bpf_map ──► 具体 map 实现的数据
       ├─ BPF_PROG_LOAD   ──► bpf_prog ─► bpf_prog_aux ─► used_maps[]
       │                        │             └────────► BTF 等附加信息
       └─ BPF_LINK_CREATE ──► bpf_link ──► 挂载目标
                                └────────► bpf_prog（常见情形）

加载验证期间：bpf_verifier_env ─► bpf_verifier_state
                                      └► bpf_func_state ─► bpf_reg_state
```

图中箭头表示源码中的关联，不表示每条箭头都以同一种方式管理引用。特别是 `bpf_link` 的基类并不直接存放所有挂载目标信息，具体目标通常在专用 link 结构中；`STRUCT_OPS` 的一种 link 则持有 map，`link->prog` 为 `NULL`。[link 基类](../../linux/include/linux/bpf.h#L1747-L1769) · [XDP 专用 link](../../linux/net/core/dev.c#L10122-L10126) · [STRUCT_OPS 特例](../../linux/kernel/bpf/bpf_struct_ops.c#L1342-L1389)

## 2. 入口数据：`union bpf_attr` 与 `struct bpf_insn`

`bpf()` 的三个参数是 `cmd`、`union bpf_attr *` 和 `size`。`cmd` 决定怎样解释同一块 `attr` 内存：创建 map 时读取 `map_type/key_size/value_size/max_entries`；加载程序时读取 `prog_type/insn_cnt/insns` 等；创建 link 时读取 `prog_fd`、挂载目标和 `attach_type`。因此 `bpf_attr` 是**按命令复用的请求容器**，不是加载后留在内核里的 BPF 对象。[调用入口](../../linux/kernel/bpf/syscall.c#L6307-L6310) · [map 属性](../../linux/include/uapi/linux/bpf.h#L1484-L1502) · [程序属性](../../linux/include/uapi/linux/bpf.h#L1560-L1594) · [link 属性](../../linux/include/uapi/linux/bpf.h#L1766-L1780)

内核先检查属性长度、将缺失部分清零、复制用户数据，再按照 `cmd` 分发。这样同一个 UAPI 结构可以随命令扩展；`size` 也是协议的一部分。[`__sys_bpf()`](../../linux/kernel/bpf/syscall.c#L6160-L6200) · [命令枚举](../../linux/include/uapi/linux/bpf.h#L937-L978)

`struct bpf_insn` 是一条指令的公开表示：`code`、4 位的 `dst_reg/src_reg`、`off` 和 `imm`。加载器把 `insn_cnt` 条指令放在 `attr.insns` 指向的区域；内核复制到 `prog->insnsi` 后再交给验证器。此时 fd 等用户态句柄可以通过伪指令编码参与加载，验证器会解析这些引用，不能把所有 `imm` 都理解为最终运行时的普通整数。[指令格式](../../linux/include/uapi/linux/bpf.h#L61-L87) · [指令复制](../../linux/kernel/bpf/syscall.c#L3016-L3023) · [伪 map FD 编码](../../linux/include/uapi/linux/bpf.h#L1311-L1323) · [验证器解析](../../linux/kernel/bpf/verifier.c#L25038-L25062)

按这个布局，一个 `bpf_insn` 占 8 字节；加载 64 位立即数的 `ldimm64` 使用相邻两个指令槽。因此 `insn_cnt` 和 `prog->len` 计数的是指令槽，不能直接当成 C 语句数。以加载 map 地址为例，提交时 `src_reg = BPF_PSEUDO_MAP_FD`、`imm = map_fd`，验证器把这个用户态句柄解析成实际的 map 指针，并记录程序对 map 的引用。[双槽编码](../../linux/include/uapi/linux/bpf.h#L1311-L1323) · [解析入口](../../linux/kernel/bpf/verifier.c#L20918-L20943)

## 3. 加载后保留的程序对象：`bpf_prog` 与 `bpf_prog_aux`

`struct bpf_prog` 放执行最直接需要的内容；`struct bpf_prog_aux` 放生命周期、验证结果和附加元数据。二者由 `prog->aux` 与 `aux->prog` 相互关联，分配时建立关系。[程序结构](../../linux/include/linux/bpf.h#L1701-L1745) · [辅助结构](../../linux/include/linux/bpf.h#L1588-L1699) · [分配与关联](../../linux/kernel/bpf/core.c#L100-L139)

它们是**分别分配的两块内存**：`bpf_prog` 连同末尾的指令区一起分配，`aux` 单独分配。指令重写可能需要扩容程序区，`bpf_prog_realloc()` 会保留原来的 `aux` 并更新 `aux->prog`。这也解释了为什么读加载路径时会看到程序指针发生变化，而辅助信息仍被保留。[空间计算](../../linux/include/linux/filter.h#L1052-L1062) · [分别分配](../../linux/kernel/bpf/core.c#L100-L126) · [扩容并保留 aux](../../linux/kernel/bpf/core.c#L256-L282)

```text
程序内存： [ bpf_prog 的固定字段 | insnsi[0] | insnsi[1] | … ]
                    │ aux                         指令区
                    ▼
辅助内存： [ bpf_prog_aux ]
                    ├─ prog ──► 当前程序内存
                    ├─ used_maps ──► map 指针数组
                    └─ btf / attach_btf / func / …
```

| 结构与字段 | 读法 |
| --- | --- |
| `prog->type`、`expected_attach_type` | 说明程序类别和预期挂载类型；后者只对部分程序类型有意义。[字段](../../linux/include/linux/bpf.h#L1718-L1719) |
| `prog->len`、`insnsi[]` | 指令槽数与指令区；`insnsi` 是结构末尾的柔性数组。[长度](../../linux/include/linux/bpf.h#L1720-L1721) · [指令区](../../linux/include/linux/bpf.h#L1732-L1737) |
| `prog->bpf_func`、`jited`、`jited_len` | 执行入口、是否已 JIT，以及生成代码的字节数；`jited_len` 与指令槽数 `len` 的单位不同。[字段](../../linux/include/linux/bpf.h#L1701-L1730) · [运行入口](../../linux/include/linux/filter.h#L732-L763) |
| `prog->stats`、`active` | per-CPU 统计和活动计数；前者记录次数、耗时等，后者可用于跟踪路径的递归保护。[统计结构](../../linux/include/linux/filter.h#L702-L707) · [递归检查实例](../../linux/kernel/trace/bpf_trace.c#L2059-L2083) |
| `aux->refcnt`、`id`、`name` | 程序引用计数、内核分配的 ID 和名称；程序的引用计数在 **aux** 中。[引用计数与 ID](../../linux/include/linux/bpf.h#L1588-L1598) · [名称](../../linux/include/linux/bpf.h#L1654-L1663) · [释放路径](../../linux/kernel/bpf/syscall.c#L2429-L2445) |
| `aux->used_maps`、`used_btfs` | 验证通过后程序保留的 map/BTF 引用集合；这是程序与这些对象生命周期相连的关键。[字段](../../linux/include/linux/bpf.h#L1645-L1667) · [验证通过后转存](../../linux/kernel/bpf/verifier.c#L25158-L25188) |
| `aux->stack_depth`、`max_ctx_offset`、`max_pkt_offset` | 验证器得到的栈深度与访问范围信息；后续运行时选择、代码生成等步骤会使用这些结果。[字段](../../linux/include/linux/bpf.h#L1592-L1595) · [解释器按栈深度选择](../../linux/kernel/bpf/core.c#L2528-L2548) |
| `aux->func`、`func_cnt`、`func_idx`、`main_prog_aux` | 关联子程序对象、记录数量与索引，并关联主程序的辅助信息；阅读 BPF 函数调用和 JIT 时再沿这些字段深入。[数量与索引](../../linux/include/linux/bpf.h#L1597-L1599) · [关联指针](../../linux/include/linux/bpf.h#L1637-L1639) |
| `aux->btf`、`func_info`、`linfo`、`jited_linfo` | 关联程序类型、函数及源码行信息；`jited_linfo` 将行信息对应到 JIT 地址。[字段及共享规则](../../linux/include/linux/bpf.h#L1666-L1690) |

加载路径先建立程序对象、复制指令，再依次调用 `bpf_check()` 和 `bpf_prog_select_runtime()`，最后分配 ID、创建程序 fd。**程序 fd 是访问对象的句柄；`bpf_prog` 才是被验证和执行的对象。**承载程序的 `struct file` 最终释放时，`bpf_prog_release()` 调用 `bpf_prog_put()` 减少 `aux->refcnt`；其他内核持有者仍可让程序存活。[加载顺序](../../linux/kernel/bpf/syscall.c#L2993-L3044) · [验证至返回 fd](../../linux/kernel/bpf/syscall.c#L3083-L3124) · [文件释放回调](../../linux/kernel/bpf/syscall.c#L2429-L2455)

程序对象也不保存本次执行的全部现场。以解释器为例，运行函数为这次调用建立 `regs[]` 和 `stack[]`，设置帧指针与上下文参数，再执行 `insnsi`；稍后遇到的 `bpf_reg_state` 则是验证器维护的分析数据。[解释器执行现场](../../linux/kernel/bpf/core.c#L2341-L2352)

程序类型还连接两组回调：`bpf_prog_ops` 提供该类型的测试运行操作，`bpf_verifier_ops` 告诉验证器哪些 helper 和上下文字段可用。`bpf_types.h` 把类型映射到对应实现；验证时 `env->ops` 指向该类型的验证回调。这是“同一套 BPF 指令，挂在不同子系统却有不同规则”的结构依据。[两组回调定义](../../linux/include/linux/bpf.h#L1047-L1077) · [程序类型映射](../../linux/kernel/bpf/syscall.c#L2286-L2311) · [验证器类型映射](../../linux/kernel/bpf/verifier.c#L36-L46) · [`env->ops` 设置](../../linux/kernel/bpf/verifier.c#L24969-L24976)

| 接口 | 回答的问题 |
| --- | --- |
| `aux->ops->test_run` | 这种程序怎样响应测试运行请求？ |
| `env->ops->get_func_proto` | 某个 helper ID 在这种程序中是否可用，参数与返回值有什么约束？ |
| `env->ops->is_valid_access` | 程序能否以指定宽度和读写方向访问这个上下文字段？ |
| `env->ops->convert_ctx_access` | 已允许的上下文访问怎样改写为实际内核结构访问？ |

表中接口定义在 [`bpf_prog_ops` / `bpf_verifier_ops`](../../linux/include/linux/bpf.h#L1047-L1078)。XDP 的回调表同时给出了 helper、上下文检查与转换函数，可以作为一个完整实例阅读。[XDP 回调表](../../linux/net/core/filter.c#L11193-L11203)

`get_func_proto()` 返回的 `struct bpf_func_proto` 把 helper 的实现地址与验证约束放在一起：`func` 指向实现，`arg_type[]` 描述五个参数，`ret_type` 描述结果，还可要求 GPL 兼容或标记可能睡眠。下面摘录 map lookup 的实际原型；验证器据此要求第一个参数是 map 指针、第二个参数指向合法 key，并将返回值标为可能为空的 map value 指针。[原型结构](../../linux/include/linux/bpf.h#L895-L916) · [原型获取与限制检查](../../linux/kernel/bpf/verifier.c#L11500-L11555) · [逐参数检查](../../linux/kernel/bpf/verifier.c#L11613-L11619)

```c
const struct bpf_func_proto bpf_map_lookup_elem_proto = {
	.func		= bpf_map_lookup_elem,
	.gpl_only	= false,
	.pkt_access	= true,
	.ret_type	= RET_PTR_TO_MAP_VALUE_OR_NULL,
	.arg1_type	= ARG_CONST_MAP_PTR,
	.arg2_type	= ARG_PTR_TO_MAP_KEY,
};
```

来源：[`bpf_map_lookup_elem_proto`](../../linux/kernel/bpf/helpers.c#L49-L56)。

## 4. map：公共头部与具体实现

`struct bpf_map` 是 map 的公共部分。`map_type` 选择实现；`key_size/value_size/max_entries` 描述容量形状；`ops` 指向操作表；`id/name` 用于识别；`btf` 与类型 ID 可补充类型信息。`refcnt` 控制整个对象最终释放，`usercnt` 另行记录具有用户持有语义的引用，二者不能当作同一个“fd 个数”。[公共结构](../../linux/include/linux/bpf.h#L295-L339) · [引用释放](../../linux/kernel/bpf/syscall.c#L911-L989)

`bpf_map_ops` 把公共层和具体 map 分开：有些回调只从系统调用使用，有些回调由系统调用和 BPF 程序共用。`map_create()` 用 `map_type` 索引操作表并调用 `map_alloc()`；具体实现分配包含公共头部的完整对象，再返回其中的 `bpf_map` 地址。反向查找专用结构时，可以用 `container_of(map, 专用类型, map)`。[操作表](../../linux/include/linux/bpf.h#L83-L130) · [类型选择](../../linux/kernel/bpf/syscall.c#L1409-L1429) · [调用分配器](../../linux/kernel/bpf/syscall.c#L1507-L1513) · [返回公共头部的实例](../../linux/kernel/bpf/ringbuf.c#L190-L214) · [`container_of` 实例](../../linux/kernel/bpf/arraymap.c#L890-L896)

三个实现展示了“公共头部 + 专用数据”的不同方向：

| map 类型 | 专用结构里增加什么 | 应读的实现 |
| --- | --- | --- |
| ARRAY | `bpf_array` 内嵌 `bpf_map`，另有元素大小、索引掩码及值区/指针区 | [结构](../../linux/include/linux/bpf.h#L2076-L2086) · [操作表](../../linux/kernel/bpf/arraymap.c#L793-L818) |
| HASH | `bpf_htab` 内嵌 `bpf_map`，另有 bucket、元素管理器、计数和哈希参数；元素保存 hash 后接 key/value | [结构与元素](../../linux/kernel/bpf/hashtab.c#L88-L129) · [操作表](../../linux/kernel/bpf/hashtab.c#L2254-L2273) |
| RINGBUF | `bpf_ringbuf_map` 内嵌 `bpf_map`，持有独立的环形缓冲区指针 | [结构](../../linux/kernel/bpf/ringbuf.c#L27-L84) · [操作表](../../linux/kernel/bpf/ringbuf.c#L354-L367) |

这个布局解释了为什么只看 `bpf_map` 无法推断所有 map 的存储方式。用户态通过 map fd 操作，程序通过 helper 调用对应的 `map->ops`；同名的 lookup/update 在不同 map 上仍受各自实现约束。[用户态更新](../../linux/kernel/bpf/syscall.c#L1783-L1835) · [程序 helper](../../linux/kernel/bpf/helpers.c#L35-L78)

公共字段的单位也要结合类型解释：ARRAY 的 `max_entries` 是槽位数，`elem_size` 是对齐后的实际元素步长；RINGBUF 要求 `key_size/value_size` 为零，`max_entries` 表示缓冲区的字节容量。[ARRAY 元素布局](../../linux/kernel/bpf/arraymap.c#L86-L105) · [RINGBUF 容量检查与分配](../../linux/kernel/bpf/ringbuf.c#L190-L214)

生命周期要看两种计数：`bpf_map_inc()` 增加 `refcnt`，`bpf_map_inc_with_uref()` 同时增加 `refcnt` 和 `usercnt`；map 文件的释放回调通过 `bpf_map_put_with_uref()` 归还两种引用，bpffs pin 也会取得带用户持有语义的引用。`usercnt` 到零可触发 `map_release_uref`，只要 `refcnt` 仍非零，map 本体就继续存在。[增引用](../../linux/kernel/bpf/syscall.c#L1628-L1638) · [减引用与文件释放](../../linux/kernel/bpf/syscall.c#L924-L989) · [pin 取得 map 引用](../../linux/kernel/bpf/inode.c#L71-L79)

验证器记录程序使用的 map 时增加 `refcnt`，不增加 `usercnt`；对可睡眠程序还会增加 `sleepable_refcnt`。这些引用在程序释放过程中归还。这使 map 的生存期可以跨过创建它的用户态文件的生存期。[验证器取得引用](../../linux/kernel/bpf/verifier.c#L20885-L20915) · [程序归还引用](../../linux/kernel/bpf/core.c#L2902-L2924)

`PROG_ARRAY` 提供了区分两种计数的实际例子：最后一个用户引用退出时，`map_release_uref` 安排清空数组中的程序指针、释放其持有的程序引用；此时 map 本体可能还被某个程序引用。这里发生的是“清理 map 持有的程序”和“最终回收 map”两个阶段。[PROG_ARRAY 清理](../../linux/kernel/bpf/arraymap.c#L1149-L1163) · [清理回调注册](../../linux/kernel/bpf/arraymap.c#L1209-L1227)

## 5. link：一次挂载关系的对象化

`struct bpf_link` 的公共字段有 `refcnt/id/type/ops/prog/attach_type` 等，`bpf_link_ops` 提供 `release`、`dealloc`、`detach`、更新程序等回调。对于持有程序的常见 link，通用层先调用 `release` 拆除挂载，再归还程序引用并调用 `dealloc` 释放专用结构。若该类型提供 `dealloc_deferred`，回收还会经过相应的 RCU 宽限期。[link 结构与操作表](../../linux/include/linux/bpf.h#L1747-L1793) · [通用释放顺序](../../linux/kernel/bpf/syscall.c#L3241-L3293)

以 XDP 为例，`bpf_xdp_link` 在公共 `bpf_link` 之外增加网卡指针和标志。创建时先初始化 link、预留 ID/fd/file，再挂到设备；成功后才安装 fd。释放时，XDP 的 `release` 拆除设备上的挂载，`dealloc` 释放专用结构。**挂载目标不在公共 `bpf_link` 字段中，必须追到具体 link 类型。**[XDP link 结构](../../linux/net/core/dev.c#L10122-L10126) · [创建流程](../../linux/net/core/dev.c#L10589-L10642) · [XDP 回调](../../linux/net/core/dev.c#L10469-L10503) · [fd 安装](../../linux/kernel/bpf/syscall.c#L3425-L3479)

XDP 的 `link->dev` 只是受 RTNL 保护的设备关联，link 本身不长期持有设备引用；创建结束会 `dev_put()`，设备卸载 XDP 时会将 `link->dev` 置空。因此图中的指针箭头不能一律读成“目标对象的引用计数增加了一次”。[设备指针](../../linux/net/core/dev.c#L10122-L10126) · [释放临时设备引用](../../linux/net/core/dev.c#L10634-L10636) · [设备侧自动拆挂载](../../linux/net/core/dev.c#L10313-L10340)

`STRUCT_OPS` 的 map 型 link 则用 `map_fd` 取得 map，初始化时明确传入 `prog = NULL`，之后保存 map 指针。它没有注册 `release` 回调，注销挂载、归还 map 引用和释放 link 都在专用 `dealloc` 中完成。读通用 link 结构时，必须结合具体类型理解其持有关系。[`STRUCT_OPS` 创建](../../linux/kernel/bpf/bpf_struct_ops.c#L1342-L1389) · [操作表](../../linux/kernel/bpf/bpf_struct_ops.c#L1333-L1339) · [专用回收](../../linux/kernel/bpf/bpf_struct_ops.c#L1199-L1211)

link 文件的最终释放会减少 link 引用；最后一个对象引用退出时才执行回收流程。显式 `BPF_LINK_DETACH` 则通过可选的 `ops->detach` 提前拆除挂载，link 对象可以继续存在。[文件释放](../../linux/kernel/bpf/syscall.c#L3316-L3329) · [最后引用处理](../../linux/kernel/bpf/syscall.c#L3265-L3293) · [显式 detach](../../linux/kernel/bpf/syscall.c#L5885-L5905)

## 6. 验证器状态：只存在于加载分析中

`bpf_check()` 为一次验证分配 `bpf_verifier_env`，完成后释放。它指向待验证的 `prog`，并维护待分析路径栈、当前状态、已访问状态、每条指令的辅助数据，以及临时发现的 map/BTF 集合。[`bpf_verifier_env`](../../linux/include/linux/bpf_verifier.h#L730-L802) · [分配](../../linux/kernel/bpf/verifier.c#L24943-L24976) · [释放](../../linux/kernel/bpf/verifier.c#L25211-L25223)

一条路径的抽象状态可以继续拆成两层：

```text
bpf_verifier_env.cur_state
    └─ bpf_verifier_state：当前指令、分支、引用与锁状态
         └─ frame[curframe] → bpf_func_state：当前调用帧
                                  ├─ regs[]：各寄存器的抽象值
                                  └─ stack[]：各栈槽的抽象状态
```

`bpf_verifier_state` 的 `frame[]` 支持子程序调用帧，`parent/branches` 记录分支探索关系；`bpf_func_state` 保存这一帧的寄存器、调用点和抽象栈。每个状态可以代表一组可能的运行情况，验证器通过分支分析和状态剪枝检查程序。[路径状态](../../linux/include/linux/bpf_verifier.h#L362-L425) · [调用帧](../../linux/include/linux/bpf_verifier.h#L274-L322) · [状态剪枝](../../linux/kernel/bpf/verifier.c#L20403-L20440)

理解 `bpf_reg_state` 时，可以把字段分成以下几组：

| 字段 | 验证器知道什么 |
| --- | --- |
| `type` | 值是未初始化、标量、上下文指针、map value 指针等哪一类。[值类别](../../linux/include/linux/bpf.h#L960-L976) |
| `map_ptr`、`btf/btf_id` | 指针来自哪个 map，或者指向哪个 BTF 类型；它们为边界和类型检查提供依据。[来源字段](../../linux/include/linux/bpf_verifier.h#L46-L65) |
| `off`、`var_off` | 对指针，分别记录固定偏移和变量偏移的知识；对标量，`var_off` 描述值本身，`off` 还可记录同 ID 标量间的常量差。[固定部分](../../linux/include/linux/bpf_verifier.h#L37-L44) · [变量部分](../../linux/include/linux/bpf_verifier.h#L112-L118) |
| `smin_value/smax_value`、`umin_value/umax_value` 及 32 位范围 | 从有符号、无符号及位宽不同的角度约束同一个值或变量偏移。[范围字段](../../linux/include/linux/bpf_verifier.h#L119-L131) |
| `id`、`ref_obj_id` | 前者用于关联同源值或指针，后者用于跟踪需要归还的资源引用。[身份与引用](../../linux/include/linux/bpf_verifier.h#L132-L196) |

`var_off` 使用 `struct tnum { value, mask }`，用位信息描述哪些位已知、哪些位未知。比如一个标量被约束为 `0..7`，数值范围记录上下界，位信息还可表达其高位全为零；两类信息共同支持后续运算和边界检查。[`tnum` 定义与语义](../../linux/include/linux/tnum.h#L1-L17)

栈也按同样思路建模。一个 `bpf_stack_state` 描述 8 字节栈区：`slot_type[8]` 逐字节记录未初始化、普通数据、已知零或寄存器 spill 等状态；`spilled_ptr` 保存被暂存到栈上的寄存器抽象信息。这样把指针存入栈、随后取出时，验证器仍能追踪它的来源和约束。[栈状态结构](../../linux/include/linux/bpf_verifier.h#L213-L238) · [栈槽与 R10 偏移对应](../../linux/include/linux/bpf_verifier.h#L309-L321)

一个具体例子是普通 map 的 `bpf_map_lookup_elem()`：helper 原型声明返回“map value 指针或 NULL”。执行 `if (p)` 的抽象分析后，非空路径上的类型可收紧为 map value 指针，空路径上的值变为零；同源别名也会同步更新。这些都是对可能值的分析信息，实际的 map 数据仍保存在 map 中。[helper 返回类型](../../linux/kernel/bpf/helpers.c#L49-L56) · [NULL 分支状态传播](../../linux/kernel/bpf/verifier.c#L16750-L16802) · [条件跳转中的调用](../../linux/kernel/bpf/verifier.c#L17251-L17264)

验证通过后，内核为 `aux->used_maps/used_btfs` 分配数组并复制指针记录，将已有引用的释放责任交给程序；map 和 BTF 对象本体没有被复制。`used_btfs` 的元素还是 `btf_mod_pair`，同时记录 BTF 和可选的内核模块指针，程序释放时也要归还模块引用。失败路径负责归还尚未转交的集合。[转存及失败清理](../../linux/kernel/bpf/verifier.c#L25158-L25203) · [`btf_mod_pair`](../../linux/include/linux/bpf.h#L1550-L1553) · [BTF 与模块引用释放](../../linux/kernel/bpf/core.c#L2926-L2944)

路径状态等工作区在验证流程中逐步清理，最后释放 `env`；`aux` 中保留下来的验证结果则继续服务于程序。这条转换标出了加载期分析数据与加载后对象元数据的边界。[路径状态清理](../../linux/kernel/bpf/verifier.c#L23519-L23534) · [调用清理](../../linux/kernel/bpf/verifier.c#L23683-L23688) · [env 最终释放](../../linux/kernel/bpf/verifier.c#L25217-L25223)

## 7. BTF：类型记录与内核索引对象

BTF 也有两层：UAPI 格式中的 `btf_header` 给出类型段和字符串段相对于头部结束位置的偏移，每条 `btf_type` 用 `name_off/info/(size|type)` 描述一个类型。`info` 编码 kind 和随 kind 解释的数量，例如结构体成员数或函数参数数；联合字段 `size` 对结构体等类型表示大小，`type` 对指针、typedef 等类型表示所引用的类型 ID。内核的 `struct btf` 则保存已解析的数据块、类型索引、字符串、引用计数与对象 ID。[BTF 头与类型记录](../../linux/include/uapi/linux/btf.h#L11-L87) · [内核 BTF 对象](../../linux/kernel/bpf/btf.c#L253-L279)

`BPF_BTF_LOAD` 经解析后为 BTF 对象分配 ID 和 fd。map 可以由 `btf_fd` 取得 BTF，并保存 key/value 类型 ID；程序的 `aux->btf` 可保存自身函数/行信息对应的 BTF，`aux->attach_btf` 则用于描述挂载目标。**这些 BTF 指针表达不同关系，不能合并成一个“程序的 BTF”。**[BTF 对象加载](../../linux/kernel/bpf/btf.c#L8030-L8055) · [map 关联 BTF](../../linux/kernel/bpf/syscall.c#L1529-L1562) · [程序 BTF](../../linux/kernel/bpf/verifier.c#L18804-L18829) · [挂载目标 BTF](../../linux/kernel/bpf/syscall.c#L2947-L3008)

## 8. 一个容易混淆的名字：两种“程序数组”

`struct bpf_prog_array` 是挂载子系统可用于组织**多个待执行程序**的内核数组，元素指向 `bpf_prog`，例如 tracepoint 路径会在 RCU 读侧遍历它。`BPF_MAP_TYPE_PROG_ARRAY` 则是公开的 **map 类型**，其实现位于 `arraymap.c`，可供程序间 tail call 使用。名字接近，但一个是挂载点的运行列表，一个是 map 对象。[运行列表结构](../../linux/include/linux/bpf.h#L2175-L2200) · [遍历执行](../../linux/include/linux/bpf.h#L2283-L2309) · [tracepoint 使用](../../linux/kernel/trace/bpf_trace.c#L127-L149) · [PROG_ARRAY map 操作表](../../linux/kernel/bpf/arraymap.c#L1209-L1227) · [解释器的 tail call 路径](../../linux/kernel/bpf/core.c#L2096-L2125)

| 比较项 | `struct bpf_prog_array` | `BPF_MAP_TYPE_PROG_ARRAY` |
| --- | --- | --- |
| 元素 | `items[]` 中的 `bpf_prog_array_item`，包含程序指针及 cookie 或 cgroup storage | `bpf_array.ptrs[]` 中的程序指针 |
| 执行方式 | 挂载路径遍历列表，空 `prog` 标记结束 | tail call 按索引选择一个目标程序 |
| 引用与用户接口 | 填充列表的内核调用者负责维持程序引用 | 用户态更新提交程序 fd，内核取得程序引用；查询元素返回程序 ID |

依据：[运行列表布局与引用约定](../../linux/include/linux/bpf.h#L2176-L2199)、[fd 转指针并更新 map](../../linux/kernel/bpf/arraymap.c#L890-L920)、[PROG_ARRAY 取得及释放程序引用、查询 ID](../../linux/kernel/bpf/arraymap.c#L954-L1001)。

## 9. 用引用关系复盘一次加载

下面以使用一个 map、通过 XDP link 挂到网卡的程序为例，串起各对象的持有关系。

先明确一层文件关系：`dup()` 可以让多个 fd 指向同一个 `struct file`。只有这个文件的最后引用退出并执行 `.release`，才会归还它所持的 BPF 对象引用。因此下面关注的是对象引用是否仍有持有者，不能仅按关闭 fd 的次数计算。[复制 fd 时共享 file](../../linux/fs/file.c#L1298-L1305) · [文件引用归零](../../linux/fs/file_table.c#L579-L582) · [调用 release](../../linux/fs/file_table.c#L504-L505)

1. `BPF_MAP_CREATE` 分配具体 map，公共头部初始化引用计数，分配 ID 和 map fd。[创建 map](../../linux/kernel/bpf/syscall.c#L1413-L1429) · [引用计数与 fd](../../linux/kernel/bpf/syscall.c#L1507-L1527) · [发布对象](../../linux/kernel/bpf/syscall.c#L1594-L1615)
2. `BPF_PROG_LOAD` 分配 `prog + aux`，复制指令；验证器识别被引用的 map 并增加其 `refcnt`，验证成功后把 map 指针保存到 `aux->used_maps`，然后发布程序 fd。[程序分配](../../linux/kernel/bpf/core.c#L100-L139) · [map 引用](../../linux/kernel/bpf/verifier.c#L20885-L20915) · [引用转存](../../linux/kernel/bpf/verifier.c#L25158-L25173) · [程序 fd](../../linux/kernel/bpf/syscall.c#L3089-L3124)
3. `BPF_LINK_CREATE` 建立 XDP link，link 持有程序和挂载信息。关闭程序 fd 后，link 所持的程序引用仍可使程序存活；关闭 map fd 后，程序所持的 map 引用仍可使 map 存活。[XDP link 创建](../../linux/net/core/dev.c#L10589-L10642) · [link 的程序引用释放](../../linux/kernel/bpf/syscall.c#L3241-L3254) · [map 引用释放路径](../../linux/kernel/bpf/syscall.c#L954-L978)
4. 最后一个 XDP link 引用释放时，通用层调用具体 `release` 拆挂载，并在合适的时机释放 link 和程序引用。程序的最终回收流程会归还它持有的 map 引用；map 的 `refcnt` 最终归零时，才移除 ID 并安排底层实现回收。[link 回收](../../linux/kernel/bpf/syscall.c#L3241-L3329) · [程序释放 map](../../linux/kernel/bpf/core.c#L2902-L2924) · [释放工作调用](../../linux/kernel/bpf/core.c#L2950-L2970) · [map 回收](../../linux/kernel/bpf/syscall.c#L954-L978)

fd、ID、pin 也应分清：fd 是进程手里的句柄；ID 是按对象类型注册的查找编号；`BPF_OBJ_PIN` 让 BPF 文件系统保存对象引用，`BPF_OBJ_GET` 再取回 fd。**不要只凭 fd 是否关闭判断对象是否消失。**[ID 注册表](../../linux/kernel/bpf/syscall.c#L62-L67) · [pin/get](../../linux/kernel/bpf/inode.c#L478-L553) · [对象命令](../../linux/kernel/bpf/syscall.c#L3147-L3178)
