# 0.1 阅读方法与分析边界

> **本节源码**：[`Makefile`](../../linux/Makefile)、[`init/main.c`](../../linux/init/main.c)、[`include/linux/init.h`](../../linux/include/linux/init.h)
> **关键函数**：`start_kernel()`、`setup_arch()`、`mm_core_init()`、`sched_init()`、`rest_init()`
> **前置知识**：C 语言、指针与结构体、操作系统基本概念

## 概述

内核源码不是按教材章节排列的程序，也没有一个函数能解释所有运行行为。同一套源码会因为架构、配置、硬件能力和启动参数而形成不同的执行路径。本书先固定分析基线，再围绕具体问题追踪关键对象与状态变化，最后用运行时观测检验判断。阅读时应建立一条可以复查的证据链，而不是从一张调用图直接推导整个系统的行为。

## 分析基线：先明确“正在读什么”

本书的版本号取自仓库实际文件：

[`Makefile:2-5`](../../linux/Makefile#L2-L5)（v6.18.60）

```makefile
VERSION = 6
PATCHLEVEL = 18
SUBLEVEL = 60
EXTRAVERSION =
```

分析架构固定为 x86_64，默认配置是 [`linux/.config`](../../linux/.config)，其中 `CONFIG_X86_64=y`、`CONFIG_SMP=y`。这里的对称多处理（Symmetric Multiprocessing，SMP）表示内核具备多 CPU 支持，不代表运行机器恰好有多少 CPU。虚拟机的实际 CPU 数由虚拟硬件和启动过程共同决定。

把一个内核行为拆成以下四层，能避免许多误判：

| 层次 | 要回答的问题 | 证据 |
|---|---|---|
| 源码 | 这个版本是否实现了该机制？ | 定义、调用点、注释、错误分支 |
| 构建配置 | 相关实现是否被编译，选择了哪个变体？ | `.config`、`Kconfig`、`Makefile`、编译命令 |
| 运行时条件 | 当前机器是否走这条路径？ | 硬件能力、启动参数、运行时开关、对象状态 |
| 实验观测 | 本次负载实际触发了什么？ | 日志、事件、计数器及采集条件 |

例如，“源码中存在某事件”“内核编译了事件跟踪”“本次启用了事件”“缓冲区中保留了这次事件”是四个不同判断，不能互相替代。构建与运行环境的核验见 [0.2](02-environment.md)，观测链的核验见 [0.4](04-observability.md)。

## 阅读对象：以状态为中心，而不只看函数

每次阅读先写下一个可回答的问题。与其问“内存管理如何工作”，不如先问“某次分配失败后，调用者会立即返回，还是进入回收或等待”。问题越具体，越容易确定入口、边界与验证办法。

对每个关键对象记录以下内容：

- **身份**：这个结构体表示一次请求、一个共享资源，还是一个长期存在的管理对象？
- **生命周期**：在哪里创建、发布、取得引用、撤销可见性和最终释放？
- **状态**：哪些字段决定下一步，谁可以修改这些字段？
- **并发约束**：读取或修改时是否要求持锁、关闭中断、禁止抢占，或者遵守其他同步协议？
- **失败与重试**：谁处理失败，资源是否需要回滚，是否可能睡眠后重新检查条件？

初读时不必把结构体的全部字段抄到笔记中。先保留能够解释当前问题的字段；遇到新的状态转移，再补充关联字段与保护条件。

## 主流程分析：用启动入口练习分层

`start_kernel()` 适合练习“先搭主线，再进入局部”，但它不是 CPU 执行内核的第一条指令。它之前还有架构相关的交接和入口代码，完整路径见 [1.1 启动全景](../01-boot/01-overview.md)。

以下是刻意裁剪的调用树，只保留跨子系统的几个锚点；同级节点之间仍有大量初始化工作：

```text
start_kernel()                         init/main.c
├── setup_arch()                       arch/x86/kernel/setup.c
├── mm_core_init()                     mm/mm_init.c
├── sched_init()                       kernel/sched/core.c
└── rest_init()                        init/main.c
```

*图 0-1：用于练习导航的启动调用树，不是完整启动时序*

这些调用分别位于 [`init/main.c:892`](../../linux/init/main.c#L892)、[`init/main.c:931`](../../linux/init/main.c#L931)、[`init/main.c:944`](../../linux/init/main.c#L944) 和 [`init/main.c:1071`](../../linux/init/main.c#L1071)。定义入口分别见 [`arch/x86/kernel/setup.c:886`](../../linux/arch/x86/kernel/setup.c#L886)、[`mm/mm_init.c:2708`](../../linux/mm/mm_init.c#L2708)、[`kernel/sched/core.c:8643`](../../linux/kernel/sched/core.c#L8643) 与 [`init/main.c:672`](../../linux/init/main.c#L672)。

### 第一步：先读调用点的上下文

在进入 `sched_init()` 之前，先看调用者为什么把它放在这里。原文已经给出了重要约束：

[`init/main.c:939-944`](../../linux/init/main.c#L939-L944)（v6.18.60）

```c
	/*
	 * Set up the scheduler prior starting any interrupts (such as the
	 * timer interrupt). Full topology setup happens at smp_init()
	 * time - but meanwhile we still have a functioning scheduler.
	 */
	sched_init();
```

这段代码支持的结论是：调度器的这部分初始化必须先于启动中断，完整拓扑稍后建立。它不支持“全部调度初始化都在这里完成”，也不能直接说明某个调度算法如何选任务。分析到这里，应把后两个问题留给对应章节，而不是继续无边界地下钻。

### 第二步：进入被调用函数，检查输入和交付条件

对 `setup_arch()`，先关心它接收与更新什么，完成后哪些平台信息可用了；对 `mm_core_init()`，先关心哪些内存管理基础被建立；对 `sched_init()`，先关心后续代码可以依赖哪些调度对象。局部算法只有在解释这些交付条件时才需要展开。

同样的阅读方法也适用于系统调用、设备请求与异常处理：先找入口和出口，再解释中间状态怎样变化。不要把“看过所有被调用函数”当成读懂主流程的标准。

### 第三步：识别直接调用之外的控制转移

内核还有函数指针回调、汇编跳转、宏生成的入口和异步执行。它们不一定能完整显示在语言服务器的调用层次中。

例如 `rest_init()` 中的 `user_mode_thread(kernel_init, NULL, CLONE_FS)` 是创建承载后续初始化工作的任务，不是普通的同步 `kernel_init()` 调用，见 [`init/main.c:677-692`](../../linux/init/main.c#L677-L692)。画图时应标出“创建任务”这一语义，不能只按函数参数中的名字添加一条同步调用边。

## 关键细节 / 设计考量

### 注解也是阅读线索

`start_kernel()` 的声明带有 `__init`，见 [`init/main.c:869-870`](../../linux/init/main.c#L869-L870)。该宏把函数放入 `.init.text`，定义见 [`include/linux/init.h:45-48`](../../linux/include/linux/init.h#L45-L48)；初始化结束阶段调用 `free_initmem()`，见 [`init/main.c:1435-1452`](../../linux/init/main.c#L1435-L1452)。

因此，不能因为源码里有某个初始化函数，就期待登录系统后还能反复观测它。函数的可观测时间窗口和生命周期同样属于机制的一部分；启动期验证通常要在启动前准备，而不是在启动结束后补挂探针。

### 把“事实”和“解释”分开写

推荐使用三层笔记：

1. **事实**：记录文件、行号、配置和直接可见的状态变化。
2. **解释**：说明这些状态变化解决什么问题，标明尚未核实的前提。
3. **验证**：给出可以支持或反驳判断的观测入口和工作负载。

“先关中断，再修改共享状态”是代码顺序；“这样就不需要其他同步”则是额外结论，必须继续检查是否存在其他 CPU 的并发访问。类似地，看到一处释放操作，不等于已经证明对象再无引用。

### 控制阅读范围

每节正文采用“概述 → 数据结构 → 主流程 → 关键细节 → 可观测性 → 实验 → 小结”的顺序。概述回答为什么存在这个机制，调用树提供路线，代码摘录解释局部事实；代码之间的文字负责说明条件、边界与设计取舍。

第一次阅读先掌握主流程与对象关系；第二次沿字段修改、错误路径和同步协议核对。跨章引用用于划定边界，不要求读者在一处把所有子系统读完。

## 小结

- 先固定版本、架构和配置，再讨论运行时路径。
- 用具体问题驱动阅读，以对象生命周期和状态变化组织笔记。
- 调用点的上下文往往比被调用函数的全部细节更重要。
- 区分同步调用、回调注册、任务创建和异步执行。
- 源码事实、设计解释和实验现象分别记录，结论才容易复查。
